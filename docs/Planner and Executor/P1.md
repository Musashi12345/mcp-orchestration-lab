# P1: agreed behavior and execution choice

Status, 2026-10-23: P1 planning and Docker execution are implemented. Verification uses
fixed model replies, actual MCP services, Docker, and a separate native PostgreSQL test
instance. P2 remains outside this implementation.

## Agreed behavior

- Use the same CSV registration, MCP discovery, Main Task, tool selection, and subtasks
  as DAG planning. Generate Python directly in the last stage, without translating a DAG.
- Accept one program before execution. Limited planning correction follows the D1 rule;
  the main planner does not rewrite code in response to execution results.
- Agents may still make their own model calls through the shared run allowance.
- The program arranges calls, passes results, branches on known outcomes, and can request
  parallel work. Data calculations remain in the same agents as D1/D2.
- Tool requests go through the existing broker and official MCP adapter. Program code
  gets no direct PostgreSQL, credential, arbitrary host-file, or network access.
- Save source, calls, failures, results, files, and final outputs during the run. The
  independent CSV evaluator grades declared final outputs afterward.
- P2 and execution-time code rewriting are outside this P1 step.

## Code paths

`orchestration/runtime.py` now contains the shared execution admission, MCP/worker
contexts, step records, result collection, review tracking, and final records extracted
from the existing DAG executor. `Executor` inherits those methods. Its graph scheduling
and D2 review/replacement logic remain in `executor.py`.

`planner.py` uses the same Main Task, tool choice, and subtask stages as D1/D2. For P1,
its last model response is a `PythonProgram`, checked in `programs.py` and
`program_sdk/policy.py`. It saves candidates, validation errors, accepted source as a
versioned `.py` file, source hash, program record, and handoff before execution begins.
There is no intermediate DAG. Bounded corrections happen only before acceptance.

`program_executor.py` inherits `Runtime`. It maps each assigned subtask ID to its saved
server/tool, then uses `ToolBroker` and the official MCP adapter for each call. It saves
the same WAITING/READY/RUNNING/terminal states and attempts as the graph executor. The
program cannot name a different server/tool or repeat an assigned job. A separate assigned
subtask permits another use of the same tool.

`program_container.py` owns image checks, Docker creation, bounded pipe messages,
diagnostics, and cleanup. `program_sdk/client.py` and `entrypoint.py` run inside the
container. Only the container entry point executes generated source. Python syntax
checks on the host never execute it. `service.py` selects the executor from the saved
handoff; the API and `analysis` commands accept `P1`.

## Python contract

The accepted form is one `async def run(sdk, inputs)`. It permits local assignments,
JSON values, dictionary/list indexing, comparisons, conditions, SDK calls, and returns.
Imports, loops, helper functions, arithmetic, comprehensions, exception handlers,
private/object attributes, and ordinary function calls are rejected. This deliberately
keeps data analysis inside the same agents used by D1/D2.

`inputs['datasets']` maps dataset IDs to registered file references; `inputs['task']`
contains the Main Task. The program receives no host paths, model credentials, database
connection, evaluator answers, private faults, or operation ledger.

Call `await sdk.call('assigned_subtask_id', arguments)`. A confirmed result contains
`state`, `value` (structured result), `output` (saved reference), and `error` (code/message).
The server/tool and exact worker job are checked by the shared host gate. Arguments and
final outputs may use only original files and checked references already returned to
this program. Files remain on disk, outside the container.

Use `await sdk.parallel(sdk.call(...), sdk.call(...))` for independent work. Results
keep argument order. The host applies the shared capacity limit; it drains active calls
at task-defined review thresholds and saves `PASSED_WITHOUT_MODEL`. Short programs can
leave a review unreached. P1 never asks the main planner to review or rewrite its source.

A known failure returns `FAILED` so an existing branch can choose a fallback. A successful
fallback explicitly supplies `handles=['failed_subtask_id']`. Otherwise a failed job
still makes execution fail, even if Python returns normally. An unknown outcome stops
the run; it cannot be handled as an ordinary failed result. Uncalled conditional jobs
are saved as `SKIPPED`, without invented tool attempts.

Return a JSON object with exactly the accepted program's output names. Each value is
saved as an immutable JSON artifact. Execution completion is separate from task success:
the same independent evaluator grades only declared outputs afterward. Matched batches
accept explicit `--modes D1 D2 P1`; the existing default remains D1/D2.

## Selected execution approach

Use a new CSV-only Docker runner. The user clarified that this machine is an Azure
Virtual Desktop VM and chose Docker after discussing AppContainer and Windows Sandbox.
The removed pricing runner will not be restored. PostgreSQL stays directly on Windows.

The new Dockerfile is `containers/csv_python/Dockerfile`. Its official Python 3.12 slim
base is pinned by digest. The build context includes only that file and `program_sdk`
Python files. The image contains no project agents, evaluator, CSVs, or credentials.

The selected limits are 1 CPU, 512 MiB memory (same swap ceiling), 64 PIDs, and 16 MiB
temporary space. Execution uses UID/GID 65532, no network, no host mounts, read-only root,
all Linux capabilities removed, and no new privileges. Docker's default syscall filter
remains enabled. The exact immutable image ID, SDK hash, selected controls, actual
container settings, bounded stderr, and cleanup outcome are saved per run.

Build from the project root with:

```powershell
.\scripts\lab.ps1 analysis runner-build --config configs/agents_stdio.yaml
```

Builds may need network access for the pinned official image. Runs never pull an image.
Execution refuses an image whose SDK hash differs from the current source. Generated
programs cannot build images. No host execution fallback exists. PostgreSQL stays directly
on Windows. Cancellation, timeout, or protocol failure removes the owned container;
host/daemon crashes still require reconciliation, as recorded in `docs/limitations.md`.

## Verification

`test_program_planner.py` checks direct generation, saved source, bounded correction,
mode separation, and language rejection without executing generated source. Protocol
tests check framing, byte limits, duplicate keys, nonfinite numbers, and partial reads.
`test_program_executor.py` uses real Docker and official-SDK MCP fixture processes for
sequence, parallel capacity, conditions, fallbacks, unknown outcomes, cancellation,
output/reference checks, and stale-image refusal.

The native PostgreSQL evaluation test runs D1/D2/P1 against the same real analysis
worker and the same independent numeric checker. All model replies are fixed fixtures,
marked exploratory. These tests establish software behavior, not real model quality or
an advantage for any mode. Current validation evidence is linked from `docs/Cross-check`.
