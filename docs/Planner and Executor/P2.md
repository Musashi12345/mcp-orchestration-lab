# P2: Python execution with main-planner reviews

Status, 2026-10-25: implemented, with 221 non-live tests verified across the full run and
targeted completion, plus one live-model skip. P2 uses the CSV P1 Python language and Docker isolation, with D2's host-owned
review opportunities.
The [implementation plan](P2_Implementation_Plan.md) records the build checklist.
See [validation evidence](../../reports/p2_validation_2026-10-25/README.md).

## Planning and reviews

The initial planner discovers tools, registers CSVs, creates the Main Task, selects
jobs, and generates Python directly. There is no DAG intermediate. P2 requires two
increasing completed-attempt review thresholds in the task rules, just as D2 does.
Current configurations use 1 and 2. No particular agent order is required.

At a reached threshold, the host freezes new dispatch and drains active calls before
saving a public review snapshot. Parallel draining can reach both thresholds at once;
the host then reviews them in order. A short program may leave reviews unreached.
Workers can use the model in every mode; only D2/P2 ask the main planner to review
execution. Healthy P2 reviews still make a counted request and may return `KEEP`.

The shared review context includes the original request, Main Task, datasets, tool
contracts, current breakdown and DAG/program, states, successful result references,
bounded observations, public failures, unresolved failure IDs, and remaining budgets.
It does not contain private grader calculations, expected answers, fault schedules,
provider credentials, or the effect ledger. Observations do not authorize new policy.

The decision contract is:

- `KEEP`: continue the same container, outstanding calls, and Python local variables.
- `REVISE`: return a replacement `PythonProgram`, its remaining-work `breakdown`,
  selected successful result IDs in `preserve`, and any `recoveries` declarations.
- `STOP`: save the reason, clean up, and fail with `PLANNER_STOPPED`, as D2 does.

`KEEP` and `STOP` cannot include replacement work. Invalid revisions get only the
configured bounded corrections, all charged to the same model allowance. Review
decisions, rejected candidates, errors, and corrections remain saved.

## Continuation inputs

A revision starts a fresh container after confirmed removal of the old one. Python
locals do not survive. The host supplies `inputs['task']`, `inputs['datasets']`, and
`inputs['snapshot']`. The last mapping contains only selected, host-verified successful
results, keyed by the IDs from `valid_outputs`:

```python
async def run(sdk, inputs):
    previous = inputs["snapshot"]["ARTIFACT_ID_FROM_REVIEW"]
    result = await sdk.call("remaining_job", {"summary": previous["value"]})
    return {"answer": result["value"]}
```

This is an interface example, not a runnable plan: the artifact and job IDs must come
from that run's accepted review. Each snapshot item has the same `state`, `value`,
`output`, and `error` envelope as a successful SDK call. A replacement with no assigned
jobs may return preserved values directly. Initial programs receive an empty snapshot.

The host checks run ownership, saved identity, hashes, producer success, and nested
references. An unrelated artifact in the same run is not automatically visible.
The aggregate canonical JSON envelopes selected by one revision must fit
`max_result_bytes`; this selection bound also applies to D2 snapshot bindings.
Python startup must additionally fit the existing framed-pipe byte limit. Oversized
inputs fail validation without truncation or reconstructing results through new calls.

Completed successful job IDs cannot reappear in replacement work. Reuse saved results
explicitly. The existing broker also protects exact operation identities; it does not
deduplicate arbitrary similar work under different job IDs. Confirmed failed jobs can
be intentionally retried under the same shared D2/P2 rules and consume allowance.

The `reused_results` metric counts the broker's exact-operation reuse. Explicit
snapshot selections are recorded separately in review decisions and continuation
artifacts; they do not increment that broker counter.

## Failure obligations across versions

Both D2 and P2 retain unresolved failures when replacing work. Review context supplies
stable failure IDs, qualified by their originating plan/program record. To recover one,
the review maps a new step to those IDs, for example:

```json
{
  "recoveries": {
    "remaining_job": ["PROGRAM_OR_PLAN_RECORD:failed_job"]
  }
}
```

Only success of that declared step resolves the earlier failure. Omitting the failure,
skipping the recovery, or failing again leaves an obligation and prevents `COMPLETED`.
The history retains the original failure and the recovery event. This is a shared
control added with P2; earlier D2 evidence predates this rule.

Within a fixed program version, the existing `sdk.call(..., handles=[...])` fallback
contract still applies. A model cannot classify an unknown outcome as a known failure;
unknown operations stop execution. Unconfirmed container cleanup also stops the run
with uncertainty and prevents a replacement runner from starting.

## Runtime, isolation, and evidence

P2 admits the run once and keeps one broker, official MCP adapter, worker gateway,
model allowance, tool budget, concurrency limit, and deadline across versions. No
generated source runs on the host. The Python subset and container limits are the
same as [P1](P1.md); generated code has no direct model, network, database, or file API.
Checkpoint scheduling is owned by the host and adds no new SDK method.

Each accepted version saves its source/hash, breakdown, parent review/snapshot links,
and handoff. Every runner saves its immutable image ID, actual isolation settings,
host-owned version epoch, diagnostics, and cleanup. Queued old-runner calls are replaced
without invented attempts; old session callbacks cannot dispatch against a new version.
The SDK source and its language policy remain shared with P1; the image must still pass
the usual freshness check. The existing `csv-p1` image tag is also used by P2.
If Docker lists the configured tag but cannot inspect it by name, the shared lookup
requires exactly one matching immutable image ID, verifies its tag metadata, then
applies the same Linux/SDK checks. Missing or ambiguous matches fail closed. The
resolution method is saved with runner identity; execution still never pulls an image.

Final outputs must match the active program's declarations and permitted reference
scope. Execution completion remains separate from independent answer grading. Back up
both PostgreSQL and disk evidence. Durable host-crash resume, a VM per runner, and a
research winner are not claimed; see [limitations](../limitations.md).

## Running

From the project root, with PostgreSQL configured and Docker Linux containers ready:

```powershell
.\scripts\lab.ps1 analysis runner-build --config configs/agents_stdio.yaml
.\scripts\lab.ps1 analysis plan --query "Calculate total amount" --csv fixtures/data_analysis/example.csv --config configs/agents_stdio.yaml --mode P2
.\scripts\lab.ps1 analysis execute --run RUN_ID --config configs/agents_stdio.yaml
.\scripts\lab.ps1 analysis inspect --run RUN_ID
```

Use the returned run ID. `analysis run` combines planning and execution. Planning and
execution use the configured model route and consume its allowance. A run already
started cannot be executed again; replan after source/settings changes.

Matched evaluation accepts explicit `--modes D1 D2 P1 P2`, retaining the existing D1/D2
default. Reserve the full configured allowance for each mode in a matched block.
Run `scripts/check.ps1` with `MCP_LAB_POSTGRES_TEST=1`, `MCP_LAB_DOCKER_TEST=1`, and
`MCP_LAB_CODEX_TEST=0` for deterministic integration checks. Fixed replies validate
engineering behavior; they do not establish live worker quality.
